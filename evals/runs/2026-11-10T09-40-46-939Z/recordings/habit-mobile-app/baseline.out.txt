**Key decisions**

- **Offline-first.** The core loop (check in, see streaks) works against local SQLite. Sync is optional and runs in the background, so the backend isn't on the critical path.
- **Reminders are local notifications.** Daily habit reminders are scheduled on-device, which is more reliable and cheaper than server push, and they work offline. Server push (APNs/FCM) is only for streak-at-risk nudges, re-engagement, and sync wake-ups.
- **Streaks computed from check-ins.** Store check-ins with the user's local date and timezone, and derive streaks from them rather than storing a counter. This avoids timezone and multi-device conflicts.
- **Sync is simple.** Per-record `updated_at` with last-write-wins and tombstones for deletes. Habit data rarely conflicts, so CRDTs aren't worth the cost.
- **Subscriptions are server-verified.** The client sends the purchase, and the server validates it with Apple/Google and also listens to their server notifications (renewals, refunds, grace period). The server sets the premium flag. If you'd rather not build this, RevenueCat can replace the entitlement service.
- **Sized for 200k MAU.** This is modest load: a single Postgres primary (with a read replica or PITR backups), a small Redis, and 2+ stateless API instances behind a load balancer. No microservices or Kafka needed. Sync is the main write load, and it's bursty around morning and evening check-in times.

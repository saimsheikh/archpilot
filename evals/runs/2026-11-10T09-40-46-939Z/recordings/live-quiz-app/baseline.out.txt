**Flow**
1. The host signs in through the REST API, picks a quiz, and starts a session. A short join code is stored in Redis.
2. Players enter the code, the API validates it, and each player opens a WebSocket to the gateway.
3. For each question, the engine publishes it through Pub/Sub, and every gateway node pushes it to its connected players. The 20s timer runs on the server, so client clocks don't matter.
4. Answers arrive over the WebSocket, and the scoring step updates the Redis sorted set. When the timer ends, the engine publishes the updated top ranks, and the gateways push them to everyone.
5. At the end of the quiz, final results are written to PostgreSQL.

**Design choices**
- **Redis for live state:** the leaderboard and answers are ephemeral and write-heavy, and sorted sets make ranking cheap.
- **Pub/Sub fan-out:** any gateway node can serve any player, so you can scale out. 500 players fit on a single node, but this avoids a rewrite later.
- **Server-side timer:** this prevents cheating and clock drift.

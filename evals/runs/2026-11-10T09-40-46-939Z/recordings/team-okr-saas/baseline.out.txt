12,000 users in year one is small, so I kept this to a single modular monolith on one managed Postgres instead of microservices.

**Key decisions**

- **Modular monolith**: At this scale, one deployable with clear module boundaries is cheaper to run and easier to change. The boundaries let you split out Billing or Notifications later if needed.
- **Multi-tenancy**: One shared Postgres with a `tenant_id` (company) on every table. Enforce it in a single data-access layer, and consider Postgres row-level security as a backstop against cross-tenant leaks.
- **Per-seat billing**: Stripe owns subscriptions and invoicing. Your app syncs the seat count (active members) to the Stripe subscription quantity whenever someone is invited, accepted, or removed. Handle Stripe webhooks to gate access on failed payments.
- **Self-serve onboarding**: Signup creates the organization and its first admin. Invites are emailed tokens, and accepting one adds a seat.
- **Background jobs**: Weekly check-in reminders, digests, and the quarter rollover run on a scheduler and queue, so request latency isn't affected. Redis can back the queue to avoid another piece of infrastructure.
- **Load**: Check-ins peak around the weekly cycle, but 12k users is well within one Postgres instance and a couple of app instances. Add read replicas or caching of rollup views only if dashboards get slow.

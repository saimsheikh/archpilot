# Agent system with tools

A model runs in a loop: read state, pick a tool, observe the result, repeat until done.
The reliability of the tools and the guardrails around them matter more than the prompt.

## Diagram

```mermaid
flowchart TD
  user([User]) --> orchestrator["Orchestrator: model-tool loop"]
  orchestrator --> llm["LLM API"]
  orchestrator --> tools["Tool layer: typed schemas"]
  tools --> apis["External APIs"]
  tools --> sandbox["Code sandbox"]
  tools --> data[("Business data")]
  orchestrator --> state[("Run state + checkpoints")]
  orchestrator --> approvals["Human approval queue"]
  orchestrator --> budget["Budget + rate limiter"]
  orchestrator --> traces[("Traces + evals")]
```

## Trade-offs

- **Single agent vs multi-agent:** start with one agent and good tools; add sub-agents
  only when contexts clearly separate (research vs writing) and you can measure the gain.
- **Workflow vs agent:** if you can write the steps down, a deterministic workflow with an
  LLM per step is cheaper, faster and easier to test.
- **Structured tool errors:** cost a little design upfront but let the model self-repair.
- **Checkpointing:** adds storage but makes long runs resumable and debuggable.

## Failure modes and mitigations

1. **Runaway loops.** Hard limits on steps, tokens and wall-clock per run; detect repeated
   identical tool calls.
2. **Injection via tool output.** Treat tool results as data; require approval for
   destructive or external actions; least-privilege credentials per tool.
3. **Irreversible actions.** Dry-run modes, approval gates, and undo where possible.
4. **Non-reproducibility.** Log every model input and output and tool call; replay runs
   from traces in tests.
5. **Unreadable errors.** Tools return `{code, message, hint}`, never stack traces.

## Do not use it for

- Fixed, well-understood processes: write a workflow.
- Latency-critical paths (under a second): one model call, no loop.
- Actions where a mistake is catastrophic and cannot be reviewed by a human.

# Commonly forgotten concerns

## Auth and access

- **Authentication**: who can log in and how (email, SSO, social, API keys)? Buy it unless
  there is a strong reason not to.
- **Authorization**: roles, per-object permissions, tenant isolation. Enforced in one place?
- **Service-to-service auth**: how do internal services and jobs authenticate?

## Traffic and abuse

- **Rate limits**: per user, per IP, per API key; on login and expensive endpoints first.
- **Input limits**: maximum upload size, payload size, pagination limits.
- **Bots and abuse**: signup spam, scraping, credential stuffing.

## Async work

- **Queues**: anything slower than ~1 s or calling third parties goes to a background job.
- **Idempotency**: retries happen. Payments, emails, webhooks and job handlers must be safe
  to run twice (idempotency keys, processed-event ids).
- **Retries and dead letters**: bounded retries with backoff; failed jobs go somewhere
  visible.
- **Webhooks in**: verify signatures, store events, process asynchronously.

## Operations

- **Observability**: structured logs, metrics (latency, error rate, saturation), traces with
  a request id across services, and alerts that a human will act on.
- **Health checks and deploys**: readiness checks, zero-downtime deploys, rollback plan.
- **Backups**: automated database backups, tested restore, point-in-time recovery if data
  is valuable. Object storage versioning for user files.
- **Environments**: at least local and production; staging if more than one developer.
- **Migrations**: schema changes that do not lock tables or break the running version.

## Security

- **Secrets**: stored in a secret manager or platform env vars, never in the repo; rotation
  plan.
- **Encryption**: TLS everywhere; encryption at rest for sensitive data.
- **Dependencies**: automated updates and vulnerability scanning.
- **LLM-specific**: prompt injection through user or retrieved content, tool permissions,
  output validation.

## Cost

- **Cost per request / per user**: estimate it, especially for LLM calls, media, egress.
- **Cost ceilings**: budgets and alerts; caps on per-user expensive operations.
- **Idle cost**: managed services with a high minimum bill.

## Failure modes

- **Third-party outages**: what happens when the payment, auth, email or LLM provider is
  down? Timeouts, fallbacks, degraded mode.
- **Single points of failure**: one database, one region, one worker.
- **Data consistency**: what if a step in a multi-step write fails halfway?

## Data lifecycle and privacy

- **Data deletion**: account deletion that also removes data from backups, search indexes,
  analytics and third parties within the required time.
- **Data export**: users or customers asking for their data.
- **Retention**: how long logs, events and user content are kept.
- **PII in logs**: mask or avoid it.
- **Compliance**: GDPR/CCPA basics, and HIPAA/PCI/SOC 2 if the domain requires it.

# Pre-mortem

Imagine it is twelve months after launch and the project has failed or had a serious
incident. Write the five most likely causes for **this** design, not generic ones. Cover at
least one cause from each category below, then pick the five with the highest
likelihood x impact.

For each risk give: what happens (one sentence), likelihood (low/medium/high), and one
concrete mitigation the team can actually do.

## Categories and prompts

### Scaling

- Which component hits its limit first if usage is 10x the estimate? (Usually the database,
  a single worker, or a synchronous third-party call.)
- Is there a hot partition, hot tenant or hot document?
- What happens during a traffic spike from a launch or a push notification?

### Cost

- Which line item grows faster than revenue? (LLM tokens, egress, per-seat SaaS, logs.)
- Is there an operation a single user can trigger that costs real money each time?
- What is the minimum monthly bill even with zero users?

### Vendor dependency

- Which vendor, if it raised prices 3x, shut down an API, or had a day-long outage, would hurt
  the most?
- Is data stored in a format or service that is hard to export?
- Is there an abstraction or exit plan for that vendor (even if not built yet)?

### Data-pipeline fragility

- Where does data move between systems (ETL, webhooks, sync, search indexing)?
- What happens on schema changes, partial failures, duplicates, or late data?
- How would anyone notice the data is wrong?

### Security

- What is the most valuable data, and what is the shortest path for an attacker to reach it?
- Can one tenant or user ever see another's data?
- Are there admin tools, API keys or LLM tools with more power than they need?

## Good vs weak risk entries

Weak: "The system might not scale." / Mitigation: "Make it scalable."

Good: "Postgres write load from the activity feed exceeds a single instance around 2k
writes/s." / Likelihood: medium / Mitigation: "Batch feed writes through the job queue and
add a read replica for feed reads; revisit partitioning at 1k writes/s."

## Feeding back into the design

- If a mitigation is cheap (an index, a queue, a rate limit), add it to the design now.
- If it is expensive, record it as a risk with a trigger ("revisit when ...").
- Every risk goes into `ARCHITECTURE.md` via `export_architecture_md` with its category.
